## Dcm_Lcfg Direct Location

**Why use Dcm_Lcfg_DspUds.c**: This is the C file generated by BCT (Bosch Configurator Tool) after compiling DCM configuration. It contains the static mapping table of all Routine IDs (RID). You can **directly map from RID to routine name and function pointer** in one step — faster and more accurate than project-wide grep.

**File location**:
```
Gen/{Variant}/src_out/bct/_out/Dcm_Lcfg_DspUds.c
```

**Automated script**:
```bash
python scripts/routine31_mapper.py <project_root> --rid 0x2C39
```

**Manual steps**:
1. Search `Dcm_Cfg_NormalRoutineConfig_cast` for the target RID, record `routineCommonIndex_u16`
2. In `Dcm_Cfg_RoutineExtendedConfig_cast[routineCommonIndex_u16]`, find `routineHandler_pfct`
3. Search the handler function's switch-case (case 1u=start, 2u=stop, 3u=requestResult)
4. Use function name to glob-search in RBAPLCust source directory

> **Variant selection**: Exclude Bootloader directories (`RBBLDR`, `OEMBLDR`, `BMGR`). Pick the most recently modified remaining variant. If none remain, the BCT build has not succeeded.

## Determining dataOut Signal Count

**Don't guess from source code!** Dcm_Lcfg explicitly configures the number of output signals:

In `Dcm_Lcfg_DspUds.c`, search for `{RoutineName}_RequestResults_st` struct definition and check its `outSignalConfig_past` array length:

```c
static const Dcm_RoutineSubFunctionConfigType_tst Dcm_Cfg_RBAPLCUST_2C39_IPBBrakeFluidChange_RequestResults_st =
{
    ...
    &DcmDspRc_RBAPLCUST_2C39_IPBBrakeFluidChange_RequestResultsOutSig_ast[0],  /* outSignalConfig_past */
    ...
    1,  /* numberOfOutSignals_u8 */  ← directly shows only 1 output signal
};
```

| Output signal count | Diagnostic response format | Note |
|--------------------|---------------------------|------|
| 1 | `71 03 RID dataOut1` | Only status, no detailed error code |
| 2+ | `71 03 RID dataOut1 dataOut2 ...` | Has detailed error code |

> **If only 1 output signal**: when `dataOut1 = Aborted`, **failure reason cannot be distinguished from the diagnostic response alone**. Actively mention this in the report.

## Deep Dive RBAPLEOL

### Architecture Type Determination

| Type | Detection Condition | Typical Routines | Analysis Method |
|------|---------------------|-----------------|-----------------|
| **TYPE_A** | Has `g_Sequence_PST` or `RBAPLEOL_SequenceStep_ST` array, uses `RBAPLEOL_TogglingProcess_V` | BrakeFluidChange, RepairBleed, EvacAndFill | **Sequence step method** |
| **TYPE_B** | Uses `RBAPLEOL_TogglingProcess_V` but **no** sequence array | Some 2Box routines | **Generic precondition method** |
| **TYPE_C** | **Does not** use `RBAPLEOL_TogglingProcess_V`, operates MESG variables directly | VCPInfoTriggerForSlave | **MESG state machine method** |

### Method A: Sequence Step Method (TYPE_A routines)

**Only applicable to routines with step sequences.**

Steps:
1. Extract all **active** `RBAPLEOL_SequenceStep_ST` arrays from RBAPLEOL file (filter IPB/DPB versions by SwitchSettings)
2. Record all CMDs involved in this routine (e.g. `CMD_ACTUATE_PLUNGER`, `CMD_WAIT_PLUNGER_MOVE`)
3. In `RBAPLEOL_ValvesToggling.c`, **only search these CMDs'** corresponding `case` blocks, checking conditions that set `RBAPLEOL_FctStINTERRUPTED`
4. **Must also check** general preconditions after `case RBAPLEOL_FctStRUNNING:` (around lines 1756-1796)

**Example**: BrakeFluidChange (DPB variant)
```c
static const RBAPLEOL_SequenceStep_ST l_FluidChangeSequence_PST[] = {
    { CMD_INIT_LOOP_P,        2 },
    { CMD_CHECK_LOOP,         12 },
    { CMD_ACTUATE_PSV,       PSV1|PSV2 },
    { CMD_ACTUATE_CSV,       CSV1|CSV2 },
    { CMD_ACTUATE_PLUNGER,    POS_MAX },      // ← possible failure point
    { CMD_WAIT_PLUNGER_MOVE,  NotUsed },      // ← possible failure point (RBDAT Error)
    { CMD_ACTUATE_PLUNGER,    POS_MIN },      // ← possible failure point
    { CMD_WAIT_PLUNGER_MOVE,  NotUsed },      // ← possible failure point (RBDAT Error)
    { CMD_ACTUATE_PSV,        NotUsed },
    { CMD_ACTUATE_CSV,        NotUsed },
    { CMD_WAIT,               4*1S },
    { CMD_JUMP,               1 },
    { CMD_EXIT,               NotUsed }
};
```

Then in `RBAPLEOL_ValvesToggling.c`, only check `CMD_ACTUATE_PLUNGER` and `CMD_WAIT_PLUNGER_MOVE` cases.

### Method B: Generic Precondition Method (TYPE_B routines)

If the routine uses `TogglingProcess_V` but has no step sequence:
1. Check general preconditions in `case RBAPLEOL_FctStRUNNING:` in `RBAPLEOL_ValvesToggling.c`
2. Check the routine-specific sub-function (e.g. `RBAPLEOL_InitIPB2BoxEvacAndFill_V`)

### Method C: MESG State Machine Method (TYPE_C routines)

For routines like VCPInfoTriggerForSlave:
1. Directly analyze MESG state transitions in RBAPLCUST file
2. Does not involve ValvesToggling.c

### Method D: Direct Global Buffer Assignment Search (Universal Fallback)

```bash
# Limit search to RBAPLEOL platform layer source
grep -rn "g_EOLResultBuffer_PUB\[{index}\]" rb/as/core/app/dcom/RBAPLEOL/src/
```

**Analyze assignment context**:
- Is it assigned after a condition check? (e.g. `if (xxx) g_EOLResultBuffer_PUB[2] = ErrorCode;`)
- Is it directly assigned? (e.g. `g_EOLResultBuffer_PUB[2] = RBAPLEOL_RoutineExtendedStatus;`)
- Where is `RBAPLEOL_RoutineExtendedStatus` modified?

**Key files**:
| File | Content |
|------|---------|
| `RBAPLEOL_ValvesToggling.c` | Core state machine `TogglingProcess_V`, contains extensive error code assignments |
| `RBAPLEOL_InterfaceAPL.c` | Interface functions, e.g. `ValidRoutineResultsAvailable` |
| `RBAPLEOL_{SpecificRoutine}.c` | Specific routine implementations |

### Checking Request Sequence

| Scenario | `31 01` Result | `31 03` Expected Result |
|----------|---------------|------------------------|
| Routine not started | — | NRC 24 (requestSequenceError) |
| Routine executing | Normal | dataOut1 = Executing |
| Routine completed successfully | Normal | dataOut1 = Completed |
| Routine aborted | Possibly Aborted | dataOut1 = Aborted + dataOut2 |

> **Key experience**: If `31 01` returns Aborted, subsequent `31 03` **may theoretically return NRC 24** (depends on `LastSelectedRoutine` handling in customer code). If `31 03` still returns positive response, the routine was indeed selected and executed.

## DEM/DTC Verification

### 7.1 Confirm Available DEM Events for Current Variant

**Don't assume all DEM Events are available!** DHP Events are controlled by `RBFS_HydrActSystem` conditional compilation; different product lines (ESP/IPB/DPB, etc.) have different available Event sets.

**Quick confirmation method**:
```bash
cat rb/as/core/app/dcom/rbdhp/Diamant_Cfg/Diamant__FWUsed_dhp.txt
```

**Example for ESP product** (`MM21x48VESP4DPBxSoftECUxECC`):

| Bit | Protection State | DEM Event (FW Name) | Common Trigger | ESP Availability |
|-----|-----------------|---------------------|----------------|-----------------|
| `0x0001` | ValveFailed | `RbDhpValveOverHeatProtection` | Valve drive time too long, valve current exceeded, valve open/short | ✅ Available |
| `0x0002` | PumpMotorFailed | `RbDhpPumpMotorOverHeatProtection` | Pump motor run timeout, pump motor current exceeded, stall | ✅ Available |
| `0x0004` | HighSystemPressureFailed | `RbDhpHighSystemPressureProtection` | System pressure too high, high pressure protection triggered | ❌ IPB/DPB only |
| `0x0008` | McPressureFailed | `RbDhpMcPressureProtection` | Master cylinder pressure sensor signal drift/failure | ❌ IPB only |
| `0x0010` | IncomingPressureFailed | `RbDhpIncomingPressureProtection` | Brake line input pressure abnormal | ❌ IPB + RemoteAct only |

> **Important**: "ESP Availability" in the table is specific to the current ESP10HB project. For IPB/DPB products, availability would be completely different. Always check `Diamant__FWUsed_dhp.txt` first!

> **Note**: FW DEM Event names are `RbDhpXXXProtection`, while project DTC names may contain customer identifiers (e.g. `DTC_XiaoMi_ReturnPump_OtherCycle`). Use **FW DEM Event names** for investigation — they are more stable and cross-project universal.

### 7.2 DEM Event and Routine Failure Relationship (Must Read)

**Core logic**: DEM Event and Routine failure share the same underlying anomaly but follow two independent paths.

```
Underlying anomaly occurs (e.g. valve coil open)
        │
        ├──→ DHP protection submodule detects anomaly
        │       │
        │       ├──→ ProtectionState bit set (e.g. 0x0001)
        │       │       │
        │       │       └──→ RBAPLEOL_ValvesToggling.c periodic check
        │       │               if (ProtectionState != NotFailed)
        │       │                   → RoutineExtendedStatus = HydraulicProtectionError
        │       │                   → Routine failure (dataOut2 = 0x0D)
        │       │
        │       └──→ Dem_SetEventStatus(RbDhpValveOverHeatProtection, FAILED)
        │               → DEM Event reported → DTC stored (if debounce passes)
        │
        └──→ Does routine continue? No, already interrupted
```

**Two independent call points at code level** (using `RBDHP_ValveActuationTimeLimitation.c` as example):

```c
// Path 1: Set ProtectionState (direct cause of Routine failure)
*l_ProtectionState |= ((uint16)RBDHP_PROTECTIONSTATE_ValveFailed);

// Path 2: Report DEM Event (parallel to Routine failure, not causal)
(void)Dem_SetEventStatus(DemConf_DemEventParameter_RbDhpValveOverHeatProtection, DEM_EVENT_STATUS_FAILED);
```

**Key conclusions**:
1. **DEM Event does not cause Routine failure** — both are results of underlying anomaly
2. **Routine failure does not need DEM Event to be valid** — ProtectionState check is independent of DEM
3. **DEM Event validation value**: If corresponding DEM Event/DTC can be read on-site, it can **cross-validate** the code analysis conclusion (confirming the underlying anomaly indeed occurred)

### 7.3 DEM Event Investigation Priority by Routine Type

Different routines have different hydraulic operations, so even if multiple bits are set simultaneously, **priority should be determined by routine characteristics**:

**Routine Type A: Pump motor drive primarily (e.g. ESPEvacAndFill2020 `0x2C64`)**

| Priority | Bit | DEM Event | Priority Reason |
|----------|-----|-----------|-----------------|
| **P1 (Highest)** | `0x0002` | `RbDhpPumpMotorOverHeatProtection` | Routine directly drives RFP return pump for long runs, pump motor overload/overheat highest probability |
| **P2** | `0x0001` | `RbDhpValveOverHeatProtection` | Few valve operations in routine, only for switching paths, valve overheat probability lower |

**Routine Type B: Heavy valve drive + plunger movement (e.g. ESPRepairBleed2020 `0x2C65`)**

| Priority | Bit | DEM Event | Priority Reason |
|----------|-----|-----------|-----------------|
| **P1 (Highest)** | `0x0001` | `RbDhpValveOverHeatProtection` | Routine drives many valves (SSV/CSV/PSV/POV etc.) with high-frequency switching, longest accumulated valve drive time, highest overheat probability |
| **P2** | `0x0002` | `RbDhpPumpMotorOverHeatProtection` | Pump motor only auxiliary drive in routine, short run time, lowest overload probability |

> **Key principle**: Priority sorting is based on **routine hydraulic operation characteristics**, not bit numeric value. The same `ProtectionState` bit may have completely different investigation priority in different routines.

### 7.4 Validation Suggestions

1. **Read diagnostic tool DTC**: Check if corresponding DTC is reported (Confirmed/Pending)
2. **Time correlation analysis**: Confirm if DTC trigger time overlaps with `31 01` routine start time, to judge hardware true fault or protection false trigger
3. **Cross-validation**: If code analysis points to valve overheat and on-site DTC `RbDhpValveOverHeatProtection` exists, **cross-validation successful**; if code analysis points to valve overheat but no such DTC on-site, possible causes:
   - Debounce time not reached (DTC not yet Confirmed)
   - Event not available in current variant (conditional compilation excluded)
   - Code analysis root cause needs re-examination
4. **Don't reverse-infer**: **Cannot** conclude that a DEM Event corresponds to this Routine failure just because it exists — the same Event may trigger in other scenarios (e.g. normal driving)

**DEM config file paths**:
```bash
# Find DTC corresponding to a DEM Event
grep "RbDhpValveOverHeatProtection" Gen/*/src_out/bct/_out/Dem_Cfg_DtcId.h

# Find all DHP-related DEM Events
grep "RbDhp" Gen/*/src_out/bct/_out/Dem_Cfg_EventId.h

# Confirm which DHP DEM Events are actually compiled into current variant
ls Gen/{Variant}/src_out/appl-contain/ | grep -i dhp
```

## Quick Acceleration Techniques

### 1. Dcm_Lcfg Direct Location (Fastest!)

**Recommended**: Don't grep RID project-wide; query DCM compilation results directly:

```bash
# Step 1: Find latest variant
ls -lt Gen/*/src_out/bct/_out/Dcm_Lcfg_DspUds.c | head -1

# Step 2: In Dcm_Lcfg_DspUds.c, find RID's routineCommonIndex
grep -A 5 "0x2C64" Gen/{Variant}/src_out/bct/_out/Dcm_Lcfg_DspUds.c

# Step 3: Find function name by routineCommonIndex
grep -A 15 "Dcm_Cfg_RoutineExtendedConfig_cast\[{index}\]" Gen/{Variant}/src_out/bct/_out/Dcm_Lcfg_DspUds.c
```

> Can also use automation script: `scripts/routine31_mapper.py`

### 2. Limit Search by Prefix (Avoid Result Explosion)

**Core principle**: Based on variable/function prefix, directly limit to corresponding code directory; **don't search project-wide**.

| Prefix | Corresponding Directory | Note |
|--------|------------------------|------|
| `RBAPLCUST_*` | `rb/as/*/core/app/dcom/RBAPLCust/` | Customer layer code (routine wrapper) |
| `RBAPLEOL_*` | `rb/as/core/app/dcom/RBAPLEOL/` | Platform layer code (state machine, core logic) |
| `RBDHP_*` | `rb/as/core/app/dcom/rbdhp/` | DHP diagnostic hydraulic protection |
| `RBMESG_*` | Project-wide (MESG is global message) | RBMESG variable definitions and send/receive points |

**Examples**:
```bash
# ❌ Don't search RBDHP variables project-wide (20k+ results)
grep -rn "RBDHP_DiagnosisProtectionState" .

# ✅ Limit to rbdhp directory
grep -rn "RBDHP_DiagnosisProtectionState" rb/as/core/app/dcom/rbdhp/

# ✅ Priority search in *.h for type definitions (faster enum/macro location)
grep -rn "RBDHP_PROTECTIONSTATE" rb/as/core/app/dcom/rbdhp/api/*.h
```

### 3. Priority Search in *.h for Type Definitions

For enums, macros, types and other **definition content**, priority search `api/*.h` instead of `src/*.c`:

```bash
# Find RoutineExtendedStatus enum definition
grep -rn "RoutineExtendedStatus" rb/as/core/app/dcom/RBAPLEOL/api/*.h

# Find ProtectionState bit definition
grep -rn "RBDHP_PROTECTIONSTATE" rb/as/core/app/dcom/rbdhp/api/*.h

# Find dataOut1 macro definition
grep -rn "RoutineCompleted\|RoutineAborted" rb/as/ms/core/app/dcom/RBAPLCust/api/*.h
```

> `*.h` files are smaller with fewer results, typically 5-10x faster than searching `*.c`.

### 5. Check Compile Switch Values (Avoid Analyzing Excluded Code)

RB platform heavily uses `#if` conditional compilation. When analyzing any `#if`-guarded code, **must confirm the code block is active**:

```bash
# Find SwitchSettings_*.csv under Gen/{Variant}/out/
glob: Gen/{Variant}/out/SwitchSettings_*.csv

# Search specific switch in CSV
grep "RBFS_RBAPLEOLRemoteActFunctionality" Gen/{Variant}/out/SwitchSettings_*.csv
```

**SwitchSettings CSV format** (semicolon-separated):
```
SwitchName;SwitchValue;DefinitionFile;Line;ConfigFile;Line
RBFS_RBAPLEOLRemoteActFunctionality;RBFS_RBAPLEOLRemoteActFunctionality_OFF;...;...;...;...
RBFS_RBAPLEOLBrakeFluidChange;RBFS_RBAPLEOLBrakeFluidChange_DPB;...;...;...;...
```

> `SwitchValue` column shows the actually effective value, e.g. `RBFS_RBAPLEOLRemoteActFunctionality_OFF` means the function is not enabled.

> **Key**: If `Function Switch Value` is `1` (OFF), all code blocks wrapped by `#if (xxx == ON)` were excluded by the preprocessor at compile time — **treat as non-existent in the final binary**.

**Common switches to confirm**:
| Switch | Affected Scope |
|--------|---------------|
| `RBFS_RBAPLEOLRemoteActFunctionality` | 2Box remote execution function |
| `RBFS_RBAPLEOLBrakeFluidChange` | BrakeFluidChange routine availability (IPB/DPB/OFF) |
| `RBFS_RBAPLEOLValvesToggling` | Valve toggling function |

## Complete Lessons Learned

### 1. Positive Response != Success
`71` is only DCM framework protocol response. Routine logic-level failures are conveyed through `dataOut1/dataOut2`.

### 2. Customer vs Platform Layer
- **RBAPLCUST** is customer code, responsible for wrapper and DCM interface — **start here**
- **RBAPLEOL** is platform code, responsible for core state machine — **check when diving deeper**
- Don't confuse the two layers; investigate with clear hierarchy

### 3. Global Shared Buffer Risk
`g_EOLParamBuffer_PUB` and `g_EOLResultBuffer_PUB` are shared by all EOL routines. If another routine is requested while one is executing (or if buffer is written out-of-bounds), the current routine will fail.

### 4. Never Assume Fixed Values
`dataOut1` and `dataOut2` meanings may differ per project. Always confirm through code search.

### 5. Check Complete Communication Log
A single `31 03` response cannot locate the problem. Must combine with `31 01` response and complete communication record.

### 6. Cross-ECU Routines Need CAN Signal Chain Check
For 2Box systems (IPB + RBU), routine execution results may be affected by remote ECU status. Error codes pass through CAN — analyze the complete chain.

### 7. Hydraulic Protection Error: Code Analysis + DEM/DTC Validation
When `dataOut2 = 0x0D` (HydraulicProtectionError) or other hydraulic execution abnormalities:
- **Code analysis is main line**: `RBAPLEOL_ValvesToggling.c` → `RBDHP_DiagnosisProtectionState` → submodules, can fully derive protection trigger cause
- **DEM/DTC is validation means**: If customer provides field data later, confirm corresponding DEM Event through `Dem_SetEventStatus` call points
- **Use FW DEM Event names** (e.g. `RbDhpValveOverHeatProtection`) rather than project-specific DTC names, FW names are more stable and cross-project universal
- **Must filter unavailable DEM Events**: For ESP products, only `RbDhpValveOverHeatProtection` and `RbDhpPumpMotorOverHeatProtection` are available; IPB/DPB products may have pressure-related Events. Don't prompt user to check a non-existent Event
- DTC trigger time vs routine execution time correlation analysis can judge **hardware true fault** vs **protection false trigger**

### 8. Leverage BCT Generated Files for Static Mapping Queries
BCT-generated `Dem_Cfg_*.h` files contain complete DEM Event → DTC mapping, more suitable for quick queries than source code. Suggest building an index once at project start for reuse.

### 9. Must Verify Compile Switches (SwitchSettings.csv)
RB platform heavily uses `#if` conditional compilation. **Before analyzing any `#if`-guarded code, confirm the code block is active**:
- **Don't** search `#define` in source (may find multiple inactive definitions)
- **Must** check `Gen/{Variant}/out/SwitchSettings_*.csv` for actual effective values
- If `SwitchValue` is `OFF`, code block was excluded by preprocessor — **treat as non-existent**
- **Typical cases**: `RBFS_RBAPLEOLRemoteActFunctionality=OFF` means `RBAPLEOL_Are2BoxConditionsGood()` check does not exist; `RBFS_RBAPLEOLBrakeFluidChange=DPB` means use DPB version step sequence not IPB

### 10. Use DBC and Network Config to Locate Signals
By searching `MappingNET2XPASS.csv` or `.arxml` files, you can quickly establish **application layer variable ↔ CAN signal ↔ network message** mapping relationships — key tool for cross-ECU issue location.

### 11. Cross-ECU Routine Errors Need Bidirectional Investigation
2Box system routines involve IPB and RBU two ECUs; `04 05` error source is in **RBU**, but symptom shows in **IPB** diagnostic response. Investigation cannot only look at IPB side code, must:
1. Confirm what error RBU reported through CAN signal
2. Analyze the error generation conditions in RBU side code
3. If necessary, read diagnostic data and measurements from both ECUs simultaneously

## Code Path: `RB_IsAppHydrAccessPossible()` Returns FALSE

### Function Location
```
rb/as/core/hwp/hsw/rbhydr/src/ControlApp/RBHYDR_AppActAccess.c
```

### Source Implementation
```c
boolean RB_IsAppHydrAccessPossible(void)
{
  #if(RBFS_RBHYDRManageValvesInTasks == RBFS_RBHYDRManageValvesInTasks_None)
    return RBHYDR_AppActAccessGranted;
  #else
    return RBHYDR_AppActAccessGranted && RBVLV_is_vr_physically_detected_as_vr_on();

}
```

### Meaning
Judges **whether current application layer (App/Diag) can execute hydraulic actions**. Returning `FALSE` means hydraulic access is unavailable, routine will be rejected or interrupted.

### Root Cause Classification for Returning FALSE

| Category | Specific Cause | Investigation Method |
|----------|---------------|---------------------|
| **Permission not granted** | `RBHYDR_AppActAccessGranted == FALSE` | Check hydraulic access arbitration result (see below) |
| **VR physically not on** | `RBVLV_is_vr_physically_detected_as_vr_on() == FALSE` | Check VR physical state logger (see below) |

#### 1) `RBHYDR_AppActAccessGranted == FALSE` Root Causes

`RBHYDR_AppActAccessGranted` is set by **RBHYDR hydraulic access arbitration module**:

```
File: rb/as/core/hwp/hsw/rbhydr/src/HWAccessControl/RBHYDR_HydrAccessControl.c
Key lines: 717-718
```

```c
RBHYDR_AppActGrantedHydrAccess(accessGroup_idx,
    ( (control_granted_to == RBHYDR_Requester_AppAct)
   || (control_granted_to == RBHYDR_Requester_AppActViaBLM) ));
```

Meaning: Application layer hydraulic access is only granted when the current cycle's hydraulic access winner is **`AppAct`** or **`AppActViaBLM`**.

**RBHYDR requester priority (low to high)**:
```
Low priority
  └── Safety requests (SupplyBaseSafety / MotorSafety / VLVSafety)
  └── ValveCoilRelaxAfterRBDiagAct
  └── RBDiagAct / RBDiagCoToM          ← diagnostic routines may occupy
  └── ValveCoilRelaxAfterAppAct
  └── AppCAV
  └── AppActViaBLM
  └── AppAct                              ← application hydraulic request priority
  └── AppCoToM                            ← CoToM test has higher priority
  └── ValveSafetyASWReleaseRelevant
  └── PSCValveSafetyASWReleaseRelevant
  └── MotorSafetyASWReleaseRelevant
  └── SupplyBaseSafetyASWReleaseRelevant
  └── FSLSafetyASWReleaseRelevant
  └── HWEnablePath                        ← highest priority
High priority
```

**Common scenarios causing AppAct not to win**:

| Scenario | Occupying Requester | Note |
|----------|-------------------|------|
| Safety triggered | SupplyBaseSafety / MotorSafety / VLVSafety | System safety mechanism executing (e.g. overpressure, overtemperature) |
| Other diagnostic routine running | RBDiagAct / RBDiagCoToM | Another diagnostic routine occupying hydraulic |
| Release relevant test not ended | *ASWReleaseRelevant | System release test not yet complete |
| Hardware enable path active | HWEnablePath | Hardware layer requires closing hydraulic path |
| Pump motor LoadDump | MotorSafetyASWReleaseRelevant | Pump motor load dump protection |

**Investigation suggestions**:
- Measure `RBHYDR_AccessGroups[0].controlGrantedTo` value, confirm current winner
- Measure `RBHYDR_AccessGroups[0].requests[]` array, see which requesters are requesting
- Measure `RBHYDR_LastMotorInfo` and `RBHYDR_LastValveInfo[0]` to confirm final mapping result

#### 2) `RBVLV_is_vr_physically_detected_as_vr_on() == FALSE` Root Causes

```
File: rb/as/core/hwp/hsw/rbvlv/src/common/functional/act/RBVLV_UVRActuation.c
Function: RBVLV_is_vr_physically_detected_as_vr_on()
```

**VR (Valve Relay)** is the hardware switch powering solenoid valves. The function judges whether VR is truly on by detecting its physical feedback voltage.

4 specific reasons for returning `FALSE`:

| Logger Name | Meaning | Physical Significance |
|-------------|---------|----------------------|
| `vr_physical_ubvr_low_logger` | UB_VR voltage too low | VR supply voltage insufficient to maintain on state |
| `vr_physical_in_transition_to_off_logger` | VR in transition to off | Just issued close command, VR not yet fully disconnected (transitional) |
| `vr_physical_in_transition_to_on_logger` | VR in transition to on | Just issued open command, VR not yet fully engaged (transitional) |
| `vr_physical_wrongconditions_logger` | VR conditions wrong | UVR/UB_VR ratio abnormal, or other hardware conditions not met |

> **Note**: Only when all 4 above loggers are 0 does the function read `vr_physical_on_logger` and return TRUE.

**Investigation suggestions**:
- Measure `RBVLV_ValvePathIter[0]->uvr_data_ptr->uvr_state_ptr->vr_physical.*` various loggers
- Check UB_VR supply voltage stability
- Check time delay between VR open command and actual feedback

## Code Path: `RBMESG_RBDHP_DiagnosisProtectionState != NotFailed`

### Definition Location
```
File: rb/as/core/app/dcom/rbdhp/api/RBDHP_DiagnosisProtectionState.h
```

### Enum Definition
```c
typedef enum
{
    RBDHP_PROTECTIONSTATE_NotFailed                    = 0x0000,  // No fault
    RBDHP_PROTECTIONSTATE_ValveFailed                  = 0x0001,  // Valve fault
    RBDHP_PROTECTIONSTATE_PumpMotorFailed              = 0x0002,  // Pump motor fault
    RBDHP_PROTECTIONSTATE_HighSystemPressureFailed     = 0x0004,  // High system pressure fault
    RBDHP_PROTECTIONSTATE_McPressureFailed             = 0x0008,  // Master cylinder pressure fault
    RBDHP_PROTECTIONSTATE_IncomingPressureFailed       = 0x0010   // Input pressure fault
} RBDHP_ProtectionState_t;
```

### Meaning
**DHP (Diagnosis Hydraulic Protection) diagnostic hydraulic protection state**. When the system detects any abnormal condition that may damage hydraulic actuators, it sets the corresponding protection bit, prohibiting further diagnostic hydraulic actions.

### Trigger Sources by Bit

> ⚠️ **Key reminder**: `HighSystemPressureFailed`/`McPressureFailed`/`IncomingPressureFailed` corresponding protection submodules and DEM Events are **controlled by `RBFS_HydrActSystem` conditional compilation**, typically **not compiled** in ESP/ABS/RBU product lines, so these bits **theoretically won't be set** in ESP products. Must confirm current variant actual availability (check `Diamant__FWUsed_dhp.txt`) before analysis.

| Bit | Name | Trigger Source | Common Root Cause | Typical Available Product Line |
|-----|------|---------------|-------------------|-------------------------------|
| 0x0001 | `ValveFailed` | `RBDHP_ValveActuationTimeLimitation.c` / `RBDHP_ValveActuationValueLimitation.c` | Valve execution time too long, valve drive current abnormal, valve open/short | Universal |
| 0x0002 | `PumpMotorFailed` | `RBDHP_PumpMotorActuationTimeLimitation.c` / `RBDHP_PumpMotorActuationValueLimitation.c` | Pump motor run timeout, pump motor current exceeded, pump motor stall | Universal |
| 0x0004 | `HighSystemPressureFailed` | `RBDHP_HighSystemPressureProtection.c` | System pressure too high, high pressure protection triggered | **IPB/DPB only** |
| 0x0008 | `McPressureFailed` | `RBDHP_HighSystemPressureProtection.c` | Master cylinder pressure sensor abnormal | **IPB only** |
| 0x0010 | `IncomingPressureFailed` | `RBDHP_HighSystemPressureProtection.c` | Input pressure abnormal | **IPB + RemoteAct only** |

### Core Modules Setting Protection State

```
Main module: rb/as/core/app/dcom/rbdhp/src/RBDHP_DiagnosisHydraulicProtection.c
State machine: rb/as/core/app/dcom/rbdhp/src/RBDHP_StateMachine.c
```

`RBDHP_DiagnosisHydraulicProtection.c` line 75:
```c
static uint16 g_ProtectionState = RBDHP_PROTECTIONSTATE_NotFailed;
```

Each submodule sets the corresponding bit through `|=` operation when detecting anomalies, finally broadcasting via `RBMESG_SendMESG(RBMESG_RBDHP_DiagnosisProtectionState, g_ProtectionState)`.

### Typical Trigger Scenarios

| Scenario | Set Bit | Note | Applicable Product Line |
|----------|---------|------|------------------------|
| Valve diagnostic routine (e.g. Toggle Valve) executing with valve coil open | `0x0001` | Valve drive current detection abnormal | Universal |
| Pump motor diagnostic routine running too long | `0x0002` | Pump motor timeout protection | Universal |
| System pressure abnormally rising during diagnosis | `0x0004` | High pressure protection | **IPB/DPB only** |
| Master cylinder pressure sensor signal drift/failure | `0x0008` | Pressure signal not credible | **IPB only** |
| Brake line input pressure abnormal | `0x0010` | Input pressure monitoring triggered | **IPB + RemoteAct only** |

> **Important**: These bits can **combine** (e.g. `0x0003` = ValveFailed + PumpMotorFailed) because they use bitwise OR operation. But in ESP products, actually settable bits are typically only `0x0001` and `0x0002`.

### Investigation Suggestions

1. **Read measurements**:
   - `RBMESG_RBDHP_DiagnosisProtectionState` current value (decimal or hexadecimal)
   - Convert value to binary, confirm which bits are set

2. **Locate submodule by set bit**:
   - `0x0001` → check `RBDHP_ValveActuationTimeLimitation.c` / `ValueLimitation.c`
   - `0x0002` → check `RBDHP_PumpMotorActuationTimeLimitation.c` / `ValueLimitation.c`
   - `0x0004` → check `RBDHP_HighSystemPressureProtection.c`

3. **Check DTC**:
   - Protection state abnormalities usually accompany related DTCs (e.g. valve open, pump motor overcurrent, pressure sensor fault)

4. **Time correlation**:
   - Check if protection state set time overlaps with diagnostic routine start time
   - Confirm whether the **routine itself triggered protection** (e.g. valve really broken) or **protection false triggered** (e.g. threshold too strict)

In `RBRDC_CalculateErrorStatus()`, these two conditions are **checked in parallel**:


**Investigation priority suggestions**:

| Priority | Check Condition | Reason |
|----------|----------------|--------|
| 1 | `RBDHP_DiagnosisProtectionState` | Once set, indicates clear hardware/protection anomaly detected by system, usually most direct root cause |
| 2 | `RB_IsAppHydrAccessPossible()` | If FALSE, need further distinguish permission competition vs VR physical issue |

> **Tip**: When measuring on RBU side, simultaneously read `RBRDC_ErrorStatus` and the above 4 condition variables to quickly locate which condition triggered remote error reporting.
