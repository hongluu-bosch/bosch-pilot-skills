# diagcomm-toolkit

Writes DiagComm (CAN + CAN-TP + DCM) parameters into the CusDiag stack
ARXML under `<project_root>/rb/as/<bsw>/core/app/dcom/`.

- **In scope:** CusDiag stack only.
- **Out of scope:** RBDiag, ObdDiag, AnP, CAN/CANFD baudrate — refuse politely and redirect.

---

## Path conventions (v2.0.0)

The skill is split into **two roots**. Every relative path in this
playbook follows one of two anchors — knowing which is which keeps the
agent from wasting tokens on filesystem discovery:

| Path prefix in this doc | Anchored on | Resolves to |
|---|---|---|
| `scripts/...`, `assets/...`, `reference/...` | **SKILL_ROOT** | `~/.cursor/skills/diagcomm-toolkit/...` (one bundled checkout per user, git-tracked) |
| `inputs/...`, `outputs/...`, `state/...`, `.cache/...` | **WORKSPACE_ROOT** | `<project>/.DCOM_AI/DiagComm_Toolkit_PRJ/...` (per-project, scaffolded by `--init-project`) |

**Commands** below are written as `python <skill>/scripts/pipeline.py
...` and **must be run from the project root** (`cd <project-root>`
first) — `<skill>` is the literal placeholder for the user-level
skill path (`~/.cursor/skills/diagcomm-toolkit` on Linux/macOS,
`%USERPROFILE%\.cursor\skills\diagcomm-toolkit` on Windows; substitute
the real path when typing the command). The current working directory
is how the skill discovers WORKSPACE_ROOT; all subcommands compute it
as `<cwd>/.DCOM_AI/DiagComm_Toolkit_PRJ` once at startup.
`scripts/context.py` always prints both roots so the agent knows the
resolved paths.

**First-run bootstrap** (per project, before anything else):

```bash
cd <project-root>
python <skill>/scripts/pipeline.py --init-project
```

Idempotent. Creates the workspace skeleton + copies the blank Excel
template + drops a workspace-local `.gitignore`. After that the regular
workflow (Step 0 onward) takes over.

## User input contract (read first)

Since v2.0.0, the **only** file the user hand-edits is one Excel
workbook with data-validation dropdowns: workspace
`inputs/DiagComm.xlsx`. The skill checkout is read-only at runtime
(scripts / assets / reference / tests bundled under SKILL_ROOT); the
agent owns workspace `outputs/`, `state/`, `.cache/` and **never
writes the workbook**. To reset to blank, the agent tells the user to
re-run `pipeline.py --init-project --force` — the agent never deletes
or overwrites user files itself (Hard rule 4).

**Bootstrap and migration**:

| Starting state | Run this once per project |
|---|---|
| Fresh project, never used the skill | `cd <project-root> && python <skill>/scripts/pipeline.py --init-project` |
| Existing v1.20.x in-skill workspace at `<project>/.agents/skills/diagcomm-toolkit/inputs/DiagComm.xlsx` | `cd <project-root> && python <skill>/scripts/migrate_v1_20_to_v2.py --from-skill <project-root>/.agents/skills/diagcomm-toolkit` (lifts xlsx + state + outputs + cache into the v2 workspace, rewrites `paths.base_dir` from v1 default `"../../.."` to v2 default `"../.."`) |
| Existing v1.19.x JSON+YAML inputs anywhere | `cd <project-root> && python <skill>/scripts/pipeline.py --init-project` then `python <skill>/scripts/migrate_v1_19_to_xlsx.py --legacy-from <dir-with-old-json>` |

`pipeline.py status` refuses to run with `BROKEN` status when an
obsolete layout (v1.19.x or v1.20.x in-skill) is still on disk; the
error message embeds the exact migration command.

Step 8 also needs a DOORS NT account + password **at run-time only**.
Resolution order (since 1.17.0): `--password <pwd>` → `$DOORS_PWD` env
var → OS keychain (Windows Credential Manager / macOS Keychain / Linux
Secret Service via `keyring`) → interactive `getpass` prompt. Typical
flow: first run with `--password <pwd> --save-credentials` to cache
once; thereafter just `--user-nt <NT>` and the keychain delivers the
password silently. Password rotated? Either run the cache command
again, or let the auto-refresh path catch the auth failure and prompt
once. Never store the password in any file under `inputs/` /
`outputs/` / `state/`, never echo it back in chat. See
[Step 8b — credentials](#step-8b--credentials-keyring-fallback) for the
full table and Hard rule 9 for the agent-side rules.

### Asking the user vs. asking via tools

This skill is interaction-mode neutral. When you need a
yes/no / clarification (e.g. Step 5 confirm before `apply --apply`,
Step 8 NT + password), ask the user with **plain prose in the chat
reply** — exactly the wording shown in each step. Do **not** rely on
client-side prompt tools (Cursor's `AskQuestion`, structured forms,
modal dialogs, etc.); they are not portable across LLM clients and
this skill is meant to run anywhere. The user replies with text;
"yes" / "apply" / "go" mean go, anything else means stop.

## Workflow (follow in order, never skip)

0a. *(one-time per project)* `cd <project-root> && python <skill>/scripts/pipeline.py --init-project`
0. `python <skill>/scripts/context.py`
1. User edits workspace `inputs/DiagComm.xlsx` (Sheet 'Project & Parameters').
2. `python <skill>/scripts/pipeline.py status`
3. `python <skill>/scripts/pipeline.py validate`
4. `python <skill>/scripts/pipeline.py apply --dry-run`
5. Summarize diff → ask user "Apply? (yes/no)"
6. On yes: `python <skill>/scripts/pipeline.py apply --apply`
7. Summarize workspace `outputs/FSCS.txt` + `outputs/diff_report.txt`.
7.5. *(one-time per project)* DOORS exploration loop: confirm `document_uuid`, pull the JSON dump, confirm the `anchor.by_heading` text actually matches a row — see [Step 7.5](#step-75--doors-exploration-loop-one-time-per-project-no-commits).
8. *(optional)* Upload FSCS to DOORS via `scripts/doors_sync.py` — auto-decides insert/update, builds + uploads + persists state in one shot. See [Step 8](#step-8--upload-fscs-to-doors).

All commands run from the **project root** (the directory that owns
the AUTOSAR tree). The skill discovers WORKSPACE_ROOT as
`<cwd>/.DCOM_AI/DiagComm_Toolkit_PRJ` once at startup, so `cd` is the
contract. `<skill>` resolves to wherever the user-level skill lives
(usually `~/.cursor/skills/diagcomm-toolkit/`); shell-shorthand it
with `alias dctk="python ~/.cursor/skills/diagcomm-toolkit/scripts/pipeline.py"`
if the user works on multiple projects regularly.

where the project lives, run (from the project root):

```bash

```

read-only, stdlib-only, and prints the facts the agent otherwise tends

- The six target ARXML files resolved from the current config.
- The next exact command to run.

Use machine-readable output only when scripting:

### Schema (since 1.20.0: Excel-driven)

The single user input is `inputs/DiagComm.xlsx`. Layout:

| Sheet | Owns | Edit cadence |
|---|---|---|
| `Project & Parameters` | `project.name`, `project.product_type`, all 23 `parameters.*` leaves | Every spec change |
| `Paths & Options` | `paths.*` (base_dir, dcom_root, ARXML file templates), `options.*` | Once per project; standard layout = zero edits |
| `DOORS Upload` | `doors.document_uuid`, `mode`, `upload.dry_run` | Once per project (replace placeholder UUID) |
| `README` | Field type/range cheat-sheet | Read-only |

Each row is `Field | Value | Type | Allowed/Range | Description`. Only
the **Value** column is user-editable; required cells are highlighted
red until filled, enums are dropdowns, integers/floats have range
validation. Excel enforces the contract before the user even saves.

`scripts/excel_loader.py` reads the xlsx and writes three derived
JSON/YAML files into `.cache/` (gitignored):

- `.cache/DiagComm_values.json` — `{project, parameters}` (was `inputs/DiagComm_values.json` ≤ 1.19.x)
- `.cache/DiagComm_config.json` — `{paths, options}` (was `inputs/DiagComm_config.json`)
- `.cache/doors_mapping.yaml`   — Sheet 'DOORS Upload' merged with `assets/doors_mapping_skeleton.yaml`

The runtime keeps the same internal four-block shape (`project` /
`paths` / `options` / `parameters`); every existing call site
continues to see it via `runtime.load_user_inputs()`. Cache is
auto-refreshed (mtime-based) at the start of every pipeline / DOORS
command — the user never has to "import" or re-run anything.

Two semantic axes (unchanged from v2):

| Block | Sheet | What it is | Multiplicity |
|---|---|---|---|
| `project` | `Project & Parameters` | Project identity (name + product_type). | Many `(name, product_type)` pairs may share one parameter set. |
| `parameters` | `Project & Parameters` | The unique DiagComm parameter set (incl. `CAN_Channel`). Drives the param fingerprint and every ARXML write. | Unique per upload. |
| `paths` | `Paths & Options` | Path templates the runtime resolves under `base_dir`. | Once per project layout. |
| `options` | `Paths & Options` | Default flags (`dry_run_default`, `validate_before_apply`). | Once per project. |
| `doors` (overrides) | `DOORS Upload` | The 3 user-set DOORS fields; rest comes from `assets/doors_mapping_skeleton.yaml`. | Once per project. |

Implications:
- Swapping `project.product_type` alone is *not* a parameter change → triggers an `update` (append a new `(project, product)` mapping to the same DOORS row), not a fresh insert.
- Editing anything inside `parameters` (including `CAN_Channel`) flips the fingerprint.
- Pre-1.20.0 inputs (`DiagComm_values.json`, `DiagComm_config.json`, `doors_mapping.yaml`) and v1.20.x in-skill layout both trigger a hard "BROKEN" status with the exact migration command to run.
- To reset to a blank xlsx: `python <skill>/scripts/pipeline.py --init-project --force` (the skill never overwrites the user file in normal flows; `--force` is the explicit opt-in — see Hard rule 4).

## Step 7.5 — DOORS exploration loop *(one-time per project, no commits)*

Run this **before** Step 8 the first time a project is wired up to DOORS,
or whenever DOORS-side restructuring may have changed where DiagComm
content should attach.

The point is to verify two things on a real DOORS dump:

1. The `document_uuid` set on `inputs/DiagComm.xlsx::Sheet 'DOORS Upload'` actually
   resolves to the right document.
2. The `anchor.by_heading` text (default: `"CAN ID and Timing
   Requirements"`) actually matches exactly one row in the dump, and the
   row that matches is the one DiagComm content should be inserted after.

This step writes nothing to DOORS and never asks for "yes/no". You can
re-run it freely.

### Step 7.5a — confirm the target

```bash
python <skill>/scripts/doors_helper.py show-target \
    --mapping .cache/doors_mapping.yaml
```

(The cache is auto-refreshed from `inputs/DiagComm.xlsx` first; you
don't need to do anything else.)

| Exit | Action |
|---|---|
| 0 | UUID present and looks real. Proceed. |
| 1 | The xlsx still has the placeholder `PUT-DOORS-DOCUMENT-UUID-HERE`. **Stop.** Tell the user to open `inputs/DiagComm.xlsx::Sheet 'DOORS Upload'` and paste the real UUID into the `doors.document_uuid` Value cell. |
| 2 | `doors:` block missing or `document_uuid` absent. **Stop.** |

### Step 7.5b — pull the document → JSON

Agent calls the **read-module** MCP tool from
[`reference/doors_tool_inventory.md`](reference/doors_tool_inventory.md)
with the UUID printed by `show-target`, mapped onto whatever arg name
the server expects (e.g. `module_uuid`, `doc_id`, `urn`).

Save the response to `outputs/doors_export.json`.

> The first time you do this, also append a one-line note in
> [`reference/doors_tool_inventory.md`](reference/doors_tool_inventory.md)
> recording the actual arg name. Future runs read it from there.

### Step 7.5c — inspect the JSON shape

```bash
python <skill>/scripts/doors_helper.py inspect \
    --json-file outputs/doors_export.json --depth 3
```

Surface the top-level keys to the user. The dump should contain a
`rows` array of object dicts; on Bosch DWA exports each row has an
`identifier`, an `AbsoluteNumber`, and a `DescriptionOfRequirementRB`
that carries the row's primary text body. For Object Heading rows it
holds the heading text (e.g. `"CAN ID and Timing Requirements"` —
that is what `anchor.by_heading` matches against in
`build_doors_payload.py`); for ordinary content rows like the one
DiagComm-toolkit inserts at `last_success_abs`, it holds what was
written into the `Object Text` xlsx column. There is no separate
`Object Text` / `ObjectText` key in the fetch response — same field,
two semantics; see [`reference/doors_tool_inventory.md`](reference/doors_tool_inventory.md#get_doors_module).

### Step 7.5d — confirm the anchor heading actually matches

`build_doors_payload.py` looks up the row whose
`anchor.heading_field` (default `DescriptionOfRequirementRB`) **equals**
`anchor.by_heading` (default `"CAN ID and Timing Requirements"`). To
sanity-check this on the live dump:

```bash
python <skill>/scripts/doors_helper.py extract \
    --json-file outputs/doors_export.json \
    --query "data.rows[?DescriptionOfRequirementRB=='CAN ID and Timing Requirements'].identifier"
```

> Use `inspect --depth 1` first to confirm whether the dump roots the
> rows at `rows` or `data.rows` — Bosch DWA exports use
> `data.rows`.

Expected: exactly one identifier matching the heading row's id (shape
varies per project — typically `<DOC>_SWFS_<SECTION>_NNN`).

If it returns nothing, the project's DOORS module either:
- uses different wording (e.g. `"CAN ID & Timing Requirements"`) →
  edit `anchor.by_heading` to match,
- or stores the heading in a different field → edit
  `anchor.heading_field`,
- or has no comparable row → fall back to `mode: update` in Step 8.

Once the extract returns the right scalar, you are ready for Step 8.

## Step 8 — upload FSCS to DOORS

Triggered when the user says any of: "上传 doors", "同步到 DOORS",
"upload FSCS", "import to DOORS", or volunteers it after Step 7. **Skip
this step entirely if the user does not ask for it.**

This step is fully self-contained inside `diagcomm-toolkit` — no
sibling skill needed. The recommended single entry point is:

```bash
# First time on a new machine: cache the password in the OS keychain
python <skill>/scripts/doors_sync.py --user-nt <NT> --password <pwd> --save-credentials

# Every run after that: zero password prompts, zero env vars
python <skill>/scripts/doors_sync.py --user-nt <NT>
```

The credential cache is OS-native (Windows Credential Manager / macOS
Keychain / Linux Secret Service via the `keyring` library). The
password ciphertext lives in the user's keychain, **never** on the CLI,
in chat history, or in any file under the skill tree. Detailed
fallback table: [Step 8b — credentials](#step-8b--credentials-keyring-fallback).

`doors_sync.py` does six things in one shot:

1. Auto-refreshes `.cache/` from `inputs/DiagComm.xlsx` via
   `scripts/excel_loader.py`, then reads
   `.cache/DiagComm_values.json` + `.cache/DiagComm_config.json`
   (merged) and `.cache/doors_mapping.yaml` (module_uuid + skeleton).
2. Reads `state/doors_upload_state.json` and **automatically decides
   `insert` vs `update`** — see the rule table below. No more asking
   the user.
3. Calls `scripts/build_doors_payload.py` in-process to write
   `outputs/doors_upload.xlsx` (DOORS-native xlsx via xlsxwriter).
4. Calls `scripts/doors_upload.py` (subprocess; 180 s hard timeout).
5. **(Insert path only, since 1.14.0)** Reconciles the real
   AbsoluteNumber via a fresh module fetch + set-diff against
   `outputs/doors_export.json`. The upload server's `SUCCESS:<n>` is
   an opaque counter, **not** the AbsoluteNumber DOORS allocates;
   trusting it would make every subsequent update fail with
   `Cannot find required Object`. See [Step 8c — post-insert
   reconciliation](#step-8c--post-insert-reconciliation) below.
6. On success, persists the **real** AbsoluteNumber back into
   `state/doors_upload_state.json` so the next run for the same
   `(project, product)` resolves to `update` and targets the right
   row. Update mode reuses the existing `last_success_abs` and never
   touches the upload counter.

The four helpers under the hood are still callable individually for
debug / one-off use:

- `scripts/doors_helper.py` — `show-target` / `inspect` / `extract` / `lint-*`
- `scripts/build_doors_payload.py` — Step 8b helper (build only)
- `scripts/doors_upload.py` — Step 8c helper (upload only)
- `scripts/doors_fetch.py` — fetch a module via HTTP/SSE with explicit
  timeouts (used by `doors_sync.py` for reconcile, also a standalone
  CLI for one-off exports)
- **`scripts/doors_state.py`** — state read/write + decision (imported by `doors_sync.py`)

### Auto-decision rule

`doors_sync.py` first **classifies the change** (parameter set vs.
project/product vs. FSCS prose) and then translates that classification
into `insert | update | skip`. The DOORS row tracked under each
`module_uuid` is a **living record** — most actions grow it rather than
replace it.

#### Conceptual model

| Input | Multiplicity |
|---|---|
| **Parameters** (`inputs/DiagComm.xlsx::Sheet 'Project & Parameters'::parameters.*` — note `product_type` lives in `project.*`, not here) | Unique per upload at any moment in time. |
| **(`project.name`, `project.product_type`)** | Not unique — one parameter set may serve multiple projects/products. |

Because `(project, product)` is many-to-one against the parameter set,
the DOORS row's multi-value cells (`RB_Product`,
`RB_Realizing_SWitem`) grow as a union, while `Object Text` follows
a **replace-or-append** rule depending on whether parameters changed
(see truth table below):

| Cell | What grows |
|---|---|
| `RB_Product` | Every product that has ever shared this row. Each item is translated through `value_maps.RB_Product` (e.g. `ESP` → `ESP 10`) and joined with newlines. |
| `RB_Realizing_SWitem` | Every arxml basename that has ever been part of the project's DiagComm stack under this row. |
| `Object Text` | **Replaced** with the current FSCS when parameters didn't change (`pp_only_changed` / `fscs_only_changed`); **appended** to with a thin delta-only block when parameters did change (`params_changed`). On first insert it's the current FSCS verbatim. The cell does *not* grow monotonically anymore — see [Object Text composition rules](#object-text-composition-rules-v7). |

#### Truth table

| `change_kind` | What changed since last successful run | Mode | What the row looks like afterwards |
|---|---|---|---|
| `first_insert` | (no state entry for `module_uuid`) | **insert** | Fresh row; `covered_*` lists seeded with single current values; Object Text = current FSCS verbatim. |
| `params_and_pp_changed` | Parameter fingerprint differs **AND** project or product also differs | **insert** | Brand-new DOORS row carved next to the previous one. State is **replaced** — old `covered_*` lists are gone (the orphaned row in DOORS is no longer tracked). |
| `params_changed` | Parameter fingerprint differs; project + product unchanged | **update** | Same DOORS row. Object Text gets a thin delta-only block appended (one line per changed parameter, aligned with FSCS body width — *no full FSCS replay*). `covered_arxml_paths` may grow. |
| `pp_only_changed` | Parameters identical; project and/or product differs | **update** | Same DOORS row. `covered_projects` / `covered_products` grow with the new value(s). Object Text is **replaced** with the current FSCS (no append; the body is identical to before, only the project/product header line differs). |
| `fscs_only_changed` | Parameters and project+product all identical; only the FSCS prose was regenerated | **update** | Same DOORS row. Object Text is **replaced** with the new FSCS. |
| `no_change` | Nothing tracked has changed | **skip** (exit 1) | Pass `--force-no-skip` to append a single-line "Re-uploaded with no semantic change" marker anyway. |

> "Parameters" in v2 already excludes `product_type` by construction
> (it lives at `project.product_type`, not in the `parameters` block),
> so swapping product alone never flips the fingerprint — that's
> always a project/product change, not a parameter change. The
> fingerprint is a SHA-256 over a sort-keys JSON dump of the
> `parameters` block.

#### Manual overrides

- `--force-mode insert` — always insert. State entry is replaced;
  the previous DOORS row becomes orphaned (still in DOORS, no
  longer tracked by state).
- `--force-mode update` — always update. Only valid if state already
  records a `last_success_abs` for this `module_uuid`. The
  classified `change_kind` still drives the Object Text template.
- `--force-no-skip` — when `change_kind == no_change`, upload anyway
  (Object Text gets a "Re-uploaded with no semantic change" stamp).

> **`update` mode regenerates the entire row.** `RB_Product` and
> `RB_Realizing_SWitem` come out of `(state.covered_* ∪ current run)`
> as growing unions; `Object Text` follows the v7 replace-or-append
> rule (see below). Static `RB_*` columns (`RB_Configuration`,
> `RB_Realizing_SWComponent`, …) come straight from `defaults:` in
> the mapping yaml. DOORS replaces the row at the recorded
> `AbsoluteNumber` with the freshly-built one.

### Cell content rules (v7)

| Cell | `insert` mode | `update` mode |
|---|---|---|
| `RB_Product` | Current `product_type`, mapped via `value_maps.RB_Product`. | Union of `state.covered_products` and the current `product_type`, each mapped, joined with newlines (insertion order, dedup). |
| `RB_Realizing_SWitem` | All arxml basenames in the current project's DiagComm stack, joined with newlines. | Union of `state.covered_arxml_paths` and the current run's arxmls, joined with newlines. |
| `Object Text` | Full `outputs/FSCS.txt` verbatim. | **Depends on `change_kind`** — see [Object Text composition rules](#object-text-composition-rules-v7). |

This is wired through `extras.rb_product_value`,
`extras.rb_realizing_value`, and `row.object_text` in
`assets/doors_mapping_skeleton.yaml`. Do **not** bind `Object Text` to
`extras.fscs_full_text` or `extras.fscs_hybrid_text`. Do **not** bind
`RB_Product` to `map:RB_Product:extras.product_type` (the legacy form
only ever produces the *current* product, defeating the union).

### Object Text composition rules (v7)

Since 1.15.0, the cell **stops growing monotonically**. The new rule
is "replace when parameters didn't change, append a delta-only block
when they did":

| `change_kind` | Operation | Cell content after run |
|---|---|---|
| `first_insert`, `params_and_pp_changed` | seed | current FSCS verbatim |
| `params_changed` | **APPEND** | prev cell + thin separator + delta-only block (one line per changed parameter, no FSCS replay) |
| `pp_only_changed` | **REPLACE** | current FSCS verbatim |
| `fscs_only_changed` | **REPLACE** | current FSCS verbatim |
| `no_change` (`--force-no-skip`) | APPEND | prev cell + single-line marker |

Why the asymmetry: when parameters are unchanged the FSCS body is
byte-identical to whatever's already in the cell (only the header
project/product/timestamp line differs). Re-attaching a banner +
"Refreshed FSCS" block on every `pp_only_changed` /
`fscs_only_changed` run was pure redundancy and is gone in 1.15.0.
When parameters do change, the appended delta lists the actual
old → new pairs only — the previous FSCS already sits at the top of
the cell to show what came before.

`build_payload`'s text report tags each run with `Object Text op:
REPLACE | APPEND` so it's obvious from the report alone what just
happened to the cell.

> Existing rows that were grown under the v6 always-append model will
> have their cumulative banner history preserved on the next
> `params_changed` run (the new delta block is appended on top), but
> wiped on the next `pp_only_changed` / `fscs_only_changed` run (the
> cell is replaced with the current FSCS). The history is still
> available locally in `state/doors_upload_state.json::modules[<uuid>]
> .history` regardless.

### `state/doors_upload_state.json`

- Lives at `<workspace>/state/doors_upload_state.json` (a sibling of
  the workspace's `inputs/` and `outputs/` directories — i.e. under
  `<project>/.DCOM_AI/DiagComm_Toolkit_PRJ/state/`). The folder is
  **agent-owned** — users do not edit it.
- Schema **v3** (one entry per `module_uuid`). Each entry stores the
  *latest active row* for that DOORS module:
  - `last_success_abs`, `last_upload_at`
  - `current_project_name`, `current_product_type`,
    `current_param_fingerprint`, `current_fscs_sha256` — used by
    `classify_change()`
  - `covered_projects`, `covered_products`, `covered_arxml_paths` —
    grow monotonically; drive the union for `RB_Product` /
    `RB_Realizing_SWitem` cells
  - `last_object_text` — the full `Object Text` content as last
    written; the next update appends on top of this
  - `history[]` — append-only log of every upload (`ts`, `project`,
    `product`, fingerprint, FSCS sha, `change_kind`, `abs_n`)
- A freshly initialized workspace has no state file — `--init-project`
  creates the empty `state/` directory and the first successful upload
  populates `doors_upload_state.json`. The skill checkout itself does
  **not** ship a `state/` directory anymore (v2.0.0 split).
- Legacy state files (v1 per-`(uuid, project, product)` entries; v2
  one entry per uuid without accumulation lists) are auto-migrated on
  first read. Migrated v2 entries start with `covered_*` lists seeded
  from the single recorded value and `last_object_text = null`; the
  next update appends on top of the (empty) prior text.
- See [`reference/state_recovery.md`](./reference/state_recovery.md)
  for the schema dump and the recovery procedure if you need to force
  a fresh DOORS row even though state remembers one.

### Step 8b — credentials (keyring fallback)

`doors_sync.py` resolves the DOORS password through a 4-level fallback
chain. **Pick the first non-empty source and stop.** This means: an
explicit `--password` always wins over a stale keychain entry; the
keychain wins over an interactive prompt; and CI / non-TTY shells
never block waiting for input.

| # | Source | Typical user | Notes |
|---|---|---|---|
| 1 | `--password <pwd>` CLI flag | One-off / debug | Visible on the command line — pair with `--save-credentials` to drop straight into the keychain instead. |
| 2 | `$DOORS_PWD` env var | CI / scripted runs | Set in the runner's secret store, not in `$PROFILE` (a plain-text profile defeats the purpose). |
| 3 | OS keychain entry under service `diagcomm-toolkit:doors`, account `<user_nt>` | **Default for interactive use** | Encrypted by the OS (DPAPI / Keychain / Secret Service); user-bound, not portable across machines. |
| 4 | Interactive `getpass` prompt | First-time fallback | Only when stdin is a TTY. Hidden input. Offers no save by default — pair with `--save-credentials` if you want it cached. |

Credential management commands:

| Goal | Command |
|---|---|
| Cache password the first time | `python <skill>/scripts/doors_sync.py --user-nt <NT> --password <pwd> --save-credentials --no-upload` |
| Refresh after a password change | Same as above, with the new password |
| Forget the cached password on this machine | `python <skill>/scripts/doors_sync.py --user-nt <NT> --forget-credentials` |
| Bypass keychain (CI / debug) | Add `--no-keyring`; only sources 1, 2, 4 are consulted |

**Auto-refresh on auth failure** *(since 1.17.0)*: when the upload
returns an auth-style error (`401`, `Unauthorized`, `Invalid
credentials`, `Authentication failed`, `bad/wrong password`, plus the
DWA Chinese variants `密码错误` / `用户名或密码错误` / `认证失败`)
**and** the password came from a cache (env var or keychain), the
script prompts **once** for a new password and retries. On retry
success the new password silently overwrites the keychain entry; on
retry failure the keychain is **not** touched. The script never
retries more than once per run — see the lock-out warning below.

> **NT account lock-out — read this once.** Most enterprise DOORS
> deployments delegate auth to LDAP / Active Directory, which **lock
> the NT account after 3–5 failed password attempts**. `doors_sync.py`
> therefore caps each invocation at **2** auth attempts (the cached
> one + at most one user-typed retry). If both fail with auth errors
> the agent must **stop**: tell the user to verify the password via
> the DOORS Web UI (which also clears any pending lock), and only then
> rerun. Do not retry blindly, do not loop — the next attempt could
> trip the lock counter.

### Step 8b — run `doors_sync.py` (auto decide + build + upload + persist)

The recommended invocation (after a one-time `--save-credentials` per
machine):

```bash
python <skill>/scripts/doors_sync.py --user-nt <NT>
```

Reasonable variants:

| Goal | Command |
|---|---|
| First-time setup: cache the password and run | `python <skill>/scripts/doors_sync.py --user-nt <NT> --password <pwd> --save-credentials` |
| Build the xlsx, do not upload (e.g. user wants to eyeball the file) | `python <skill>/scripts/doors_sync.py --no-upload` |
| Cache password without running an upload | `python <skill>/scripts/doors_sync.py --user-nt <NT> --password <pwd> --save-credentials --no-upload` |
| Force a brand-new DOORS row even though state has an entry | `python <skill>/scripts/doors_sync.py --force-mode insert ...` |
| Force update against a state entry that exists | `python <skill>/scripts/doors_sync.py --force-mode update ...` |
| Upload anyway when fingerprints match the last success | add `--force-no-skip` |
| One-off without touching keychain | `python <skill>/scripts/doors_sync.py --user-nt <NT> --password <pwd> --no-keyring` |

The script prints a "decision banner" before doing anything:

```
doors_sync -- Step 8 decision
  project        : MyProject
  product        : IPB
  module_uuid    : 1-aaaaaaaaaaaaaaaa-M-bbbbbbbbbbbbb
  change_kind    : pp_only_changed
  decided mode   : update   target_abs=576
  reason         : params unchanged; mapping a new (project, product) onto row (was MyProject/ESP)
  state.covered  : 1 project(s), 1 product(s), 5 arxml path(s)
```

Surface this banner to the user verbatim **before** the upload runs so
they have a chance to abort with Ctrl-C if the decision looks wrong.

What the script reads (under the hood, you don't run these yourself):

- `inputs/DiagComm.xlsx` (the user file; `excel_loader.py` rebuilds the cache from this)
- `.cache/DiagComm_values.json` (`project.name` / `project.product_type` / `parameters`)
- `.cache/DiagComm_config.json` (`paths` / `options`)
- `.cache/doors_mapping.yaml`   (module_uuid + columns + anchor + value_maps; xlsx Sheet 'DOORS Upload' merged with `assets/doors_mapping_skeleton.yaml`)
- `assets/doors_template.xlsx`  (bundled DOORS template; column-style)
- `outputs/FSCS.txt`            (parsed; full text + key-value fields)
- `outputs/diff_report.txt`     (parsed; per-arxml change list, used for delta block)
- `outputs/doors_export.json`   (only in insert mode, to find the anchor)
- `state/doors_upload_state.json` (decision input, written on success)

What it writes:

- `outputs/doors_upload.xlsx`         (the file uploaded to DOORS)
- `outputs/doors_payload_report.txt`  (human-readable build summary)
- `state/doors_upload_state.json`     (only on successful upload)

`strategy: single_row` (default) emits one aggregated row whose
`RB_Realizing_SWitem` lists every project-wide DiagComm arxml. In
`insert` mode that row carries the anchor's `AbsoluteNumber` (bare
number, e.g. `400`) in column B. In `update` mode column B is blank
and column D carries `state.last_success_abs`.

| Exit (script) | Meaning |
|---|---|
| 0 | Build + upload + state persistence all succeeded. |
| 1 | DEGRADED — usually "no semantic changes since last upload, skipping" (use `--force-no-skip` to push anyway), or build-time warnings on a successful run. |
| 2 | **Stop.** Read the printed error and `outputs/doors_payload_report.txt`. Common causes: `--force-mode update` requested but state has no abs for this key; missing `outputs/diff_report.txt`; anchor heading not found in dump (insert mode). |

### Step 8c — post-insert reconciliation

`upload_doors_module`'s `Data: SUCCESS:<n>` payload is an **opaque
upload-server counter**, not the AbsoluteNumber DOORS allocates to the
new row. We've observed it increment 1-by-1 per successful call across
modules and users (614 → 615 → 616 in three consecutive uploads, while
the inserted row was actually at AbsoluteNumber=1598). Trusting it for
`last_success_abs` makes the *next* update fail with
`FAILURE:<m>:Cannot find required Object with Absolute Number <n>`.

After every successful insert, `doors_sync.py` therefore:

1. Calls `doors_fetch.fetch_module(module_uuid, refresh=True)` over
   plain HTTP/SSE with explicit timeouts.
2. Diffs the AbsoluteNumber set in the fresh fetch against
   `outputs/doors_export.json` (the snapshot already used for the
   anchor lookup, captured **before** the upload).
3. Picks the single new AbsoluteNumber as the real
   `last_success_abs`. If concurrent edits introduce multiple new
   rows, the row whose Object Text starts with our freshly-written
   FSCS prefix wins.
4. If zero new rows are visible (the upstream DOORS replication often
   takes a few seconds to a minute), retries up to
   `--reconcile-attempts N` with `--reconcile-sleep N`-second gaps.
5. On successful reconcile, also overwrites
   `outputs/doors_export.json` with the fresh fetch — so next run's
   anchor lookup and decision logic see a current snapshot for free.
6. On persistent reconcile failure, completes the run anyway but
   emits a loud WARN with the manual recovery recipe (run
   `doors_fetch.py --refresh` after the upstream catches up; then
   patch `state.modules[<uuid>].last_success_abs` and the matching
   history entry's `abs_n` to the AbsoluteNumber of the row you find
   in DOORS).

Reconcile is **insert-only**. Update mode never trusts the upload
counter — `record_update` keeps the existing `last_success_abs` — so
the bug never affected updates. To disable reconcile (debug / tests
only), pass `--no-reconcile`.

### Step 8d — preview and upload (when *not* using `doors_sync.py`)

If, for whatever reason, you need to drive build and upload by hand,
the helpers are still callable:

```bash
# build only:
python <skill>/scripts/build_doors_payload.py [--mode update --update-abs <arxml>=<n>]

# then upload:
python <skill>/scripts/doors_upload.py outputs/doors_upload.xlsx \
    "<module_uuid>" "<user_nt>" "<password>"

# or fetch a module (with optional --refresh) for one-off inspection:
python <skill>/scripts/doors_fetch.py "<module_uuid>" "<user_nt>" --refresh \
    --out outputs/doors_export_fresh.json
```

The hand-driven path will **not** read, update, or reconcile
`state/doors_upload_state.json`. Use it only when you genuinely want
to bypass auto-decision (e.g. emergency re-upload after manually
editing the xlsx). For normal operation, prefer `doors_sync.py`.

> **Why a local script and not Cursor's `CallMcpTool`:** the DOORS
> server can sit on the upload for tens of seconds, and a Cursor MCP
> call has no per-call timeout knob — if the server stalls, the IDE
> stalls. The local script gives you a hard 180 s ceiling.

> **Why the xlsx Just Works:** `build_doors_payload.py` writes the file
> with `xlsxwriter` (DOORS-native — `Application=Microsoft Excel` +
> `sharedStrings.xml`). DOORS silently rejects xlsx written by
> openpyxl, Excel, or WPS, which used to require a separate fix step.
> That step is gone.

> **Security:** never log the password, never echo it into chat,
> never persist it under `inputs/` / `outputs/` / `state/` (state file
> never holds it; reports never quote it). The supported persistence
> *is* the OS keychain (Windows Credential Manager / macOS Keychain /
> Linux Secret Service via `keyring`); the password ciphertext lives
> there, user-bound and machine-bound. Pair `--password <pwd>
> --save-credentials` once, then drop `--password` from every
> subsequent run. Do not paste the password into the agent chat —
> have the user run the cache command themselves in their own
> terminal.

### Step 8d — verify

After a successful run (`doors_sync.py` exit 0 with `Data: SUCCESS:<n>`):

1. Re-pull the same module via the **read-module** MCP tool to a fresh
   path, e.g. `outputs/doors_verify.json`. Prefer the local script
   `python <skill>/scripts/doors_fetch.py <module_uuid> <user_nt> --refresh
   --out outputs/doors_verify.json` over `CallMcpTool` — the MCP call
   has no per-call timeout knob and may stall the IDE for tens of
   minutes after a fresh upload while DOORS replicates.
2. **Find the row by `last_success_abs`, not by `<n>`.** The
   `<n>` after `Data: SUCCESS:` is the upload-server counter, *not*
   the AbsoluteNumber DOORS allocates (insert mode reconciles to
   the real abs internally; update mode keeps the prior abs). Read
   the authoritative number from
   `state.modules[<module_uuid>].last_success_abs` and look for
   that row in the fetch.
3. Confirm the row's text body matches what you uploaded. **Field
   name gotcha:** the fetch JSON does not expose `Object Text` /
   `ObjectText`; the cell content lands under
   `row["DescriptionOfRequirementRB"]` (same field that
   Step 7.5d uses to find the anchor heading — DOORS treats it as
   the row's primary text body, see
   [`reference/doors_tool_inventory.md`](reference/doors_tool_inventory.md#get_doors_module)).
   In `update` + `params_changed` mode also confirm the delta block
   is present at the tail.
4. Confirm `state/doors_upload_state.json` now has an entry under
   `modules.<module_uuid>` with the right `last_success_abs`, the
   current project/product, and a fresh `history[]` entry whose
   `change_kind` matches what the decision banner printed. In
   `update` mode also verify `covered_projects` /
   `covered_products` / `covered_arxml_paths` grew (or stayed the
   same when nothing new was added).
5. Surface 2–3 bullets to the user (e.g. *"row 1598 updated under
   `MyProject / IPB`; covered_products now `[ESP, IPB]`; state file
   refreshed; the next run for the same params will append on top of
   this Object Text."*).

## Hard rules

1. Never modify ARXML directly. Only `apply --apply` writes ARXML.
2. Never invent parameter values. Read live ARXML non-destructively via `pipeline.py landing-report`.
3. Never run `apply --apply` without a preceding `apply --dry-run` + explicit "yes" from the user.
4. Workspace `inputs/DiagComm.xlsx` is **user-owned** — the skill never writes, deletes, or overwrites it in normal flows. The single exception is the explicit reset path `python <skill>/scripts/pipeline.py --init-project --force`, which the agent must hand back to the user to run themselves (it overwrites the workbook with the blank template). The agent never invokes `--force` on its own. (`assets/DiagComm.txt` is read-only; `assets/DiagComm_schema.json` is regenerable via `python <skill>/scripts/pipeline.py gen-schema`; `assets/inputs_template.xlsx` is regenerable via `python <skill>/scripts/build_inputs_template.py` whenever the schema changes.)
5. Never skip Step 3 (`validate`).
6. Never paraphrase commands. Use the exact strings shown above.
7. Only invoke `python <skill>/scripts/context.py` (Step 0), `python <skill>/scripts/pipeline.py` (Steps 2–6), and `python <skill>/scripts/doors_sync.py` (Step 8) for the normal workflow. The latter wraps `build_doors_payload.py` + `doors_upload.py` and writes `state/`. The two wrapped scripts are still callable individually if `doors_sync.py` is unavailable, but never invoke them as a substitute when `doors_sync.py` is the right tool.
8. Never run `pip` / `python -m pip`. The user owns their env. On `ModuleNotFoundError`, tell them to run `python -m pip install -r <skill>/scripts/requirements.txt` (covers all of Steps 2–8 — the skill is self-contained, no sibling-skill dependency).
9. **Step 8 only:** never call the DOORS MCP tools (`get_doors_module`, `upload_doors_module`, …) without an explicit "yes" from the user. Never invent DOORS module UUIDs, object identifiers, or AbsoluteNumbers — always source them from `inputs/DiagComm.xlsx::Sheet 'DOORS Upload'` (resolved into `.cache/doors_mapping.yaml` by `excel_loader.py`), `outputs/doors_export.json`, or `state/doors_upload_state.json`. The anchor identifier is *always* derived dynamically by `build_doors_payload.py`; never type one in by hand. Likewise, never type an `AbsoluteNumber` for `--force-mode update` — `doors_sync.py` reads it from state. **Never** ask the user to paste their DOORS password into the chat; tell them to run `python <skill>/scripts/doors_sync.py --user-nt <NT> --password <pwd> --save-credentials --no-upload` themselves in their terminal once, then drop `--password` from every subsequent run. **Never** run `--save-credentials` on the agent's behalf with a password the user typed earlier in the conversation — that path leaks the secret into chat history.
10. **Never** run a separate xlsx "fix" step (e.g. an external `fix_upload_file.py`) before upload. `build_doors_payload.py` writes DOORS-native xlsx (xlsxwriter, sharedStrings, `Application=Microsoft Excel`) directly. If a future upload fails with "format rejected", run `python <skill>/scripts/doors_helper.py lint-doors-xlsx --excel outputs/doors_upload.xlsx` first — do **not** try to patch the file by hand.

## Troubleshooting

| Symptom | Tell the user |
|---|---|
| `arxml not found: …` | Wrong `paths.base_dir` or wrong `project.product_type`. Open `inputs/DiagComm.xlsx` and re-check Sheet 'Project & Parameters' (`project.product_type`) + Sheet 'Paths & Options' (`paths.base_dir`). Confirm project layout. |
| `[diagcomm-toolkit] No workspace found at: <project>/.DCOM_AI/DiagComm_Toolkit_PRJ` | Project not bootstrapped. Tell the user (or run, with their go-ahead): `cd <project-root> && python <skill>/scripts/pipeline.py --init-project`. |
| `[diagcomm-toolkit] Pre-1.20.0 file detected: ...` | The 1.19.x JSON / YAML files still sit in the v2 workspace `inputs/`. Tell the user to run `python <skill>/scripts/migrate_v1_19_to_xlsx.py --legacy-from <dir-with-old-json>`, verify the populated `inputs/DiagComm.xlsx`, then delete the legacy files. |
| `[diagcomm-toolkit] v1.20.x in-skill workspace detected: <project>/.agents/skills/diagcomm-toolkit/inputs/...` | The user's data is still trapped in the old skill checkout. Tell them to run `python <skill>/scripts/migrate_v1_20_to_v2.py --from-skill <project-root>/.agents/skills/diagcomm-toolkit`. |
| `[diagcomm-toolkit] inputs Excel not found: inputs/DiagComm.xlsx` | Workspace exists but the workbook is gone. Recover via `python <skill>/scripts/pipeline.py --init-project --force`. |
| `no locator match for <param>` | Container naming differs in this project. See [`reference/landing_spots.md`](./reference/landing_spots.md); run `pipeline.py landing-report` to see where it *does* land. |
| `CAN_*_ID out of range for 11bit` | Clamp the ID or switch `CAN_ID_Format` to `"29bit"`. |
| `STmin > 127 ms` | ISO 15765-2 cap. Pick a value in `0..127` ms. |
| `N_Br >= N_Bs` or `N_Cs >= N_Cr` | Ordering rule: `N_Br < N_Bs`, `N_Cs < N_Cr`. Ask for the corrected pair. |
| `ModuleNotFoundError: lxml` / `yaml` | `python -m pip install -r <skill>/scripts/requirements.txt`. |
| Step 8: `ModuleNotFoundError: doors_helper` (or `excel_io`, `json_query`, `_log`) | The skill is missing one of its bundled modules. Reinstall the skill folder from git. |
| Step 8: `Excel template missing` | `assets/doors_template.xlsx` ships with the skill — if it is absent the install is incomplete. Restore via `git checkout -- assets/doors_template.xlsx`. Never ask the user to hand-edit the file. |
| Step 8: `anchor not found in doors_export.json` | The heading text in `anchor.by_heading` does not match any row of the dump. Re-run Step 7.5d to confirm the wording, or fall back to `--mode update`. |
| Step 8: `update mode but some arxml in the diff have no updates entry` | You picked update but didn't supply an AbsoluteNumber for every arxml in the diff. Re-ask the user, then re-run with one `--update-abs <arxml>=<n>` per arxml. |
| Step 8: `diff_report has no parseable change lines` | Last apply was a no-op. Edit `inputs/DiagComm.xlsx::Sheet 'Project & Parameters'`, re-apply, then retry. |
| Step 8: `tool not found` for `doors__*` | The DOORS MCP server uses different names — re-run [`reference/doors_tool_discovery.md`](reference/doors_tool_discovery.md) and update [`reference/doors_tool_inventory.md`](reference/doors_tool_inventory.md). |
| Step 8: `connection refused <doors-mcp-host>` | DOORS MCP server is down, you're off-VPN, or the default URL doesn't match your environment. Stop. If the server lives at a different host than the bundled default, export `DIAGCOMM_DOORS_MCP_URL=http://<host>:<port>/mcp` once (or pass `--server-url ...` per run) and retry. |
| Step 8: `ModuleNotFoundError: openpyxl` / `xlsxwriter` / `requests` | `python -m pip install -r <skill>/scripts/requirements.txt`. |
| Step 8c: `doors_upload.py` exits 1 with `[FAILED] Upload failed` and code != 0 | Read the `Message` line. `format rejected` → run `pipeline.py lint-excel`; `module locked` → another user is editing the module in DOORS. **Never** patch the xlsx by hand. (For auth failures see the rows below — `doors_sync.py` 1.17.0+ handles a single auto-retry itself.) |
| Step 8c: `doors_upload.py` hangs > 180 s | The server-side write is hung; the script will exit on its own with a timeout. Tell the user; do not retry blindly. |
| Step 8b: `[doors_sync] DOORS rejected the cached credentials.` (and a prompt for a new password) | Cached password is stale (user changed it on the DOORS side). Tell the user to type the current password at the prompt — `doors_sync.py` retries once and refreshes the keychain on success. **Do not paste** the password yourself. |
| Step 8b: `the new password was also rejected.` after the auto-retry | NT name typo, password not yet propagated, or NT account already locked from earlier failed attempts. **Stop** — tell the user to log into DOORS Web UI to confirm + unlock, then rerun. **Do not** loop `doors_sync.py` — every run burns 1–2 more auth attempts and risks tripping the LDAP / AD lockout counter (typically 3–5). |
| Step 8b: `[doors_sync] DOORS rejected the password just entered.` (no auto-retry) | The user just typed the password and it was still wrong. Same playbook as above: stop, verify via DOORS Web, then rerun. |
| Step 8b: `[doors_sync] ERROR: no DOORS password available.` | All four sources empty. First-time user: tell them to run `python <skill>/scripts/doors_sync.py --user-nt <NT> --password <pwd> --save-credentials --no-upload` once in their own terminal. CI: set `$DOORS_PWD` or pass `--password`. |
| Step 8b: `[doors_sync] WARN: keyring lookup/write failed: ...` | The OS keychain backend is broken or absent (rare on Win/macOS, occasional on minimal Linux). Fall back to `$DOORS_PWD` env var or rerun with `--no-keyring --password <pwd>` for that session. Underlying fix: install a Secret Service backend, or `pip install keyrings.alt`. |

Deeper symptoms: [`reference/internals.md`](./reference/internals.md).
