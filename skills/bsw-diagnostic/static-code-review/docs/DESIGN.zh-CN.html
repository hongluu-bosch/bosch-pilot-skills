Static Code Review 方案设计文档

本文档描述 static-code-review 便携包的设计目标、架构分层、核心组件、主要流程、失败模型和工程落地边界，面向需要维护或二次集成这套方案的工程师。

1. 目标与非目标

目标

  • 把 Kimi review 方案收敛为一个可复制到任意项目根目录的便携包。
  • 让普通用户尽量通过短提示和少量点击完成当前文件或函数的 review。
  • 将 Kimi 自由文本回复稳定落地为统一命名、可归档的正式 HTML 报告。
  • 提供结构校验和源文件新鲜度 gate，避免“报告存在但已失效”。

非目标

  • 不试图判断 finding 本身是否绝对正确，gate 只检查报告存在、格式完整、可选的新鲜度。
  • 不依赖专门的 VS Code 扩展；当前方案以规则文件、任务和脚本为主。
  • 不保证 Kimi 网页自动化在任何时间都稳定可用，网页 DOM 变化会影响 RunWeb。

2. 用户角色与使用层次

角色 主要入口 典型动作
普通用户 Cline 提示词 + VS Code 任务 打开当前文件，说 Static Code Review Current File.，其余步骤由系统自动完成。
项目集成者 .clinerules、.vscode/tasks.json、README 把便携包复制进项目，安装规则，给团队提供统一入口。
维护者 tools/kimi_review_pipeline.py 及相关脚本 维护导入、校验、gate、网页自动化和输出契约。

3. 架构概览

用户视角

用户只需要打开当前文件并触发 Static Code Review Current File.，其余步骤默认自动完成。

系统视角

系统会依次执行规则检查、AI 行为影响判断、结果融合和正式报告生成。

工程保障视角

脚本链路负责输出契约、结构校验、回归检查和问题定位，保证结果可落盘、可追踪、可回归。

交互层

Cline 提示词和 VS Code 任务面向最终用户，目标是减少命令记忆成本并统一使用路径。

工作流层

tools/kimi_review.ps1 负责统一分发 Action，如 RunWeb、Validate、Gate。

核心执行层

tools/kimi_review_pipeline.py 是核心引擎，负责 bundle 生成、响应导入、报告写入、校验和 gate。

知识层

项目规则来自 .github/skills/static-code-review-workflow，通过 .clinerules 和提示约束注入到 Cline/Kimi 流程。

推荐的默认流程是“用户两步触发 + 系统后台自动处理”。对用户来说只需打开文件并触发审查；对系统来说，底层仍会执行规则检查、AI 判断、结果融合与报告落盘。

4. 核心组件

组件 职责 说明
.clinerules 把短提示绑定到项目 review 规则 支持当前文件、选中函数、命名函数等上下文。
.vscode/tasks.json 提供用户侧一键任务入口 当前已有 Static Code Review Current File 串联任务。
tools/kimi_review.ps1 统一入口脚本 把项目根目录、报告目录、Source 等默认参数封装起来。
tools/kimi_review_pipeline.py 核心执行器 负责导入、结构校验、报告写入和 gate。
review-reports/ 正式输出目录 保存当前正式 HTML 报告，并在写入前归档现有正式报告。

5. 关键流程

5.1 当前文件 review

  1. 用户打开当前 .c 文件。
  2. 用户输入 Static Code Review Current File.
  3. 系统启动 AI 代码审查。
  4. Rule Pass 根据项目规则库执行规则检查，输出命中项及其代码位置。
  5. AI Pass 独立判断功能影响。
  6. Fusion Pass 融合两轮结果并确定最终严重级别。若 Rule Pass 命中 Review Severity 为 major 或 critical 的规则，且代码不满足该规则的显式例外条款，则 Fusion 不得省略、合并或降级该 finding。
  7. Markdown 报告中需包含 Rule Coverage 段落，列出应用的规则类别、已触发的 major/critical 规则，以及未触发的主要/严重规则类别。
  8. 系统自动生成正式 HTML 报告并写入 review-reports/，写入前先统一归档根目录里的旧正式报告。

5.2 指定函数 review

  1. 用户先选中函数，或直接说 Static Code Review Function <函数名>.
  2. Cline 尽量把 review 范围收敛到选区或命名函数。
  3. 后续规则检查、AI 判断、结果融合和报告生成流程与当前文件相同。
选中函数是最稳的函数级 review 方式。仅通过函数名触发时，是否精确收敛到函数体，取决于编辑器上下文和模型行为。

5.3 七步简图

  1. 打开当前 .c 文件。
  2. 输入 Static Code Review Current File.。
  3. AI 开始代码审查。
  4. Rule Pass 执行规则检查，输出命中项及代码位置。
  5. AI Pass 独立判断功能影响。
  6. Fusion Pass 融合两轮结果并确定最终严重级别；major/critical 规则命中除非满足规则自身显式例外，否则不得省略或降级。
  7. 生成包含 Rule Coverage 段落的 Markdown 报告。
  8. 自动生成正式 HTML 报告。

6. 输出契约

  • Kimi 原始回复必须包含 Markdown Report 和一个 ```md fenced block。
  • 同一回复必须包含 HTML Report 和一个 ```html fenced block。
  • Markdown 报告必须包含固定标题：Summary、Confirmed Findings、Open Questions、Suspected But Unconfirmed Issues、Risk Summary、Suggested Next Actions。
  • HTML 报告必须包含完整 HTML 文档结构和对应 section 标题。

这套契约是 Import、Validate、Gate 能稳定工作的前提。

7. 失败模型与错误定位

Import 失败

通常是 Kimi 回复缺少 fenced block，或导入阶段的 Markdown / HTML 结构不满足契约。

Validate 失败

说明正式报告文件缺失、为空，或标题 / 计数不符合校验规则。

Gate 失败

除结构问题外，还可能是源文件比报告更新，报告已陈旧。

RunWeb 失败

大多与 Kimi 网页 DOM 变化、登录态、上传入口变化有关，而不是报告方案本身的问题。

8. 工程落地建议

  • 把当前文件 review 和 `RunWeb` 自动化一起作为默认路径，并把失败时的校验与 gate 作为标准回归检查。
  • 团队内统一要求用 Static Code Review Current File. 和任务 Static Code Review Current File。
  • 把 Gate 结果接入人工审查流程，而不是直接替代人工判断 finding 是否成立。
  • 在项目升级时优先回归测试 Import -> Validate -> Gate 三步。
