Static Code Review Usage Guide

This guide is for end users. It explains the shortest prompt-based workflow to review the current file or a function and generate standard reports automatically.

1. What You Need to Remember

Prompts

  • Static Code Review Current File.
  • Static Code Review Selected Function.
  • Static Code Review Function .

VS Code Tasks

  • Static Code Review Setup
  • Static Code Review Current File
  • Static Code Review Selected Function
For most users, the supported paths are: run Static Code Review Current File for file-level review, or select a function and run Static Code Review Selected Function for function-level review. Both paths are more reliable than chat-triggered execution because they do not depend on Cline chat-side command approval behavior.
Understand this solution in three lines: the user only triggers review; the system runs rule checks, AI reasoning, result fusion, and report generation automatically; the script chain handles validation, regression, and troubleshooting.
Rule principle is dual-pass fusion: run a rule-based pass first, run an independent AI behavior-impact pass second, then fuse both results to decide final severity.

2. First-Time Setup

  1. Copy the entire static-code-review folder into your project root.
  2. Open the static-code-review folder and double-click review-install.cmd.
  3. This installs the project configuration needed for the review workflow (.clinerules, .vscode/tasks.json), and bootstraps local auto-approve state for compatible Cline clients on that machine.
  4. The default formal path is API review (depends on api.apiKey in %USERPROFILE%/.static-code-review/config.json). It does not depend on web chat login state. Only if you explicitly switch to the web automation path do you need to verify the web chat service login status.

3. Review the Current .c File

Steps
  1. Open the target .c file in VS Code.
  2. Run the VS Code task Static Code Review Current File

This writes formal reports directly under review-reports/ without relying on manually saving a newly created editor tab. Here, "current file" means the active source file, not a generated report HTML tab.

4. Review a Function

Recommended path

  1. Select the function in the editor.
  2. Run the VS Code task Static Code Review Selected Function

Simplified path

  1. With the file open, say Static Code Review Function .
If you want the most reliable function-only scope, select the function first and then run Static Code Review Selected Function.

5. Where Reports Are Written

  • review-reports/static-code-review-report.current-file...html
  • review-reports/static-code-review-report.current-file...zh-CN.html

The file name always contains the formal report prefix static-code-review-report.current-file, the reviewed file or function name in the middle, and the timestamp at the end. The actual review scope still appears in the report title and metadata. Formal output is HTML-first; if older markdown reports are present in the workspace, they are archived together with the matching HTML files.

Whether you review the current file, a named function, or a selected function, writing a new formal report now archives all existing formal reports in the root of review-reports/ into archive/ first. If you want to archive reports separately, you can still run Static Code Review Archive Current Reports manually.

6. Common Issues

  • No report was generated: make sure setup was completed, the active tab is the target .c source file rather than an HTML report under review-reports/, and then run Static Code Review Current File again.
  • The report content is incomplete: the imported Kimi reply was likely incomplete, so copy the full reply and run the current-file review again.
  • The report is outdated: if the source file changed after report generation, trigger the current-file review again.
