1. Goals and Non-Goals

Goals

  • Package the Kimi review workflow into a portable folder that can be copied into any project root.
  • Keep end-user operations short: prompt once, then import, validate, and gate with minimal clicks.
  • Turn Kimi free-form responses into stable, archived formal HTML review reports by normalizing the intermediate Markdown structure.
  • Provide structural validation and freshness-aware gating.

Non-Goals

  • The gate does not prove that each finding is correct; it checks report success, structure, and optional freshness only.
  • The workflow does not depend on a dedicated VS Code extension.
  • RunWeb is not guaranteed to survive Kimi web UI changes without maintenance.

3. Architecture

User View

The user only opens the current file and triggers Static Code Review Current File.. The remaining steps are automated by default.

System View

The system runs rule checks, AI behavior-impact reasoning, result fusion, and formal report generation in sequence.

Engineering Assurance View

The script chain enforces output contracts, structural validation, regression checks, and troubleshooting paths so results stay operational and traceable.

Interaction Layer

Cline prompts and VS Code tasks are optimized for end users and provide the standard workflow entry.

Workflow Layer

tools/kimi_review.ps1 dispatches the main actions such as RunWeb, Validate, and Gate.

Execution Layer

tools/kimi_review_pipeline.py is the core engine for import, report generation, validation, metadata, and gating.

Knowledge Layer

Rules and templates come from skills/static-code-review-workflow and are loaded through .clinerules.

The preferred default path is a two-step user trigger with automated backend processing. The user opens the file and starts review; the system performs rule checks, AI reasoning, fusion, and report generation behind the scenes.

5. Main Flows

5.1 Current file review

  1. The user opens the current .c file.
  2. The user says Static Code Review Current File.
  3. The system starts AI code review.
  4. Rule Pass checks the code against the project guideline library and emits rule hits with concrete code locations.
  5. AI Pass evaluates functional impact independently.
  6. Fusion Pass merges both passes and finalizes severity. If Rule Pass hits a guideline with Review Severity major or critical, Fusion must not omit, merge, or downgrade that finding unless the code satisfies an explicit exception clause in the rule, and that exception is documented in the finding Reasoning.
  7. The Markdown report must contain a Rule Coverage paragraph listing applied guideline categories, any triggered major/critical rules, and categories evaluated but not triggered.
  8. The system generates formal HTML reports under review-reports/ and archives the existing formal report files in that root first.

5.2 Function review

  1. The user selects the function, or says Static Code Review Function <name>.
  2. Cline attempts to narrow the review scope to the selection or named function.
  3. The downstream rule-check, AI reasoning, fusion, and report-generation flow stays the same.
Selection-based review is the most reliable function-level path. Name-only review depends on editor context and model behavior.

5.3 Simple 7-step flow

  1. Open the current .c file.
  2. Run the VS Code task Static Code Review Current File.
  3. AI starts source-code review.
  4. Rule pass checks guideline mappings and emits concrete rule hits.
  5. AI pass evaluates functional impact independently.
  6. Fusion pass merges both passes and finalizes severity; major/critical rule hits cannot be omitted or downgraded unless the code satisfies an explicit rule exception.
  7. Generate Markdown report with a Rule Coverage paragraph.
  8. Formal HTML reports are generated.

6. Output Contract

  • The Kimi response must contain Markdown Report followed by a ```md fenced block.
  • The same response must contain HTML Report followed by a ```html fenced block.
  • The Markdown report must contain the fixed section headings expected by the validator.
  • The HTML report must be a complete document and contain the expected section titles.

7. Failure Model

Import Failure

Usually caused by missing fenced blocks or malformed Markdown/HTML sections.

Validate Failure

Means the formal report is missing, empty, or structurally invalid.

Gate Failure

Can indicate either report structure problems or that the source file is newer than the report.

RunWeb Failure

Most often related to Kimi web UI changes, login state, or upload selector changes.

8. Rollout Recommendations

  • Use current-file review with `RunWeb` automation as the default path, and treat validation plus gate as the standard regression check.
  • Standardize on the prompt Static Code Review Current File. and the task Static Code Review Current File.
  • Treat gate as an operational quality check, not as a final judge of finding truth.
  • Regression-test the Import -> Validate -> Gate chain whenever the bundle changes.
